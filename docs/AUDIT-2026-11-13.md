## 8. 安全审计（按严重程度）

### P0-1 匿名可写/可删 24 张表（**已修复**）
所有表权限原为 `read/create/update/delete("any")`。项目 ID 与端点在前端包中公开，任何人不登录即可调用 Appwrite REST 删除成员、篡改积分、写入团队。
- 处理方式与结果见 §11、§12：25 张表已全部收敛，匿名读写实测返回 401。

### P0-2 `users` 表可被匿名改写 → 角色提权（**已修复**）
服务端 `readAppwriteSession` 从 `users.role` 解析权限；该表原本 `update("any")`，攻击者可把自己改成 `admin`。现已限制为 `users` 可读写。

### P1-1 前端直连数据库，服务端角色校验不覆盖数据写入（**设计缺陷，需迭代**）
成员/任务/积分等写操作由浏览器用 Appwrite SDK 直接落库，服务端的 `requireAdmin` 只保护 `/api/*`。匿名写入已随 P0-1 关闭；但**任何已登录成员**仍可用 SDK 绕过 UI 修改他人的积分或任务。彻底修复需把写操作迁到 `/api/*` 并加角色校验（工作量约 3–5 天），或启用 Row Security + 行级 ACL。

### P1-2 公开纪念馆页匿名读取 `members` 全字段（**已知，接受**）
`members` 保持 `read("any")` 以支撑公开页，导致匿名可读到 `email`、`feishu_profile`（含手机号）等。修复方案：新增 `/api/public/hall` 只返回 public 成员的白名单字段，再把 `members` 读权限收回。本次未做，原因是会改动公开页数据契约，需单独回归。

### P1-3 `feishu_integrations` 匿名可读（低危，**已修复**）
已核实该表**不含密钥**（仅 app_id、chat_id、开关）；随 P0-1 一并收敛为 `users`，匿名读取实测 401。

### P2 其他
- 角色矩阵页面为只读展示（设计如此）。
- 头像外链依赖飞书 CDN（可用性风险）。
- 前端未做 CSP；Vercel 默认头足够内测。

## 11. 本次已完成的修复

1. `members` 表：写权限 `any → users`（保留公开读以支撑纪念馆）。
2. `users` 表：读写全部 `any → users`，消除提权路径。

4. 复核飞书链路：`points.created` 真实投递成功（messageId 已记录）。
5. **飞书登录 → Appwrite 身份桥接**（提交 `5ab72c3`）。表权限收敛的直接障碍是：飞书 OAuth 只签发 Team Hub 自己的 JWT，浏览器在 Appwrite 侧仍是匿名，一旦把 `Any` 改成 `Users`，全体队员会立刻读不到数据。为此新增 `api/_lib/appwrite-identity.js`：服务端用 API Key 为每位成员开通 Appwrite 账号（无邮箱者用 `feishu.<openid>@teamhub.local` 占位），签发会话密钥，经 `/api/session` 下发给前端 `Client.setSession()`。密钥放在 HttpOnly Cookie（`th_aws`，30 天）里，每次启动先校验有效性，失效则重签。
6. **纪念馆寄语改走服务端**：公开页投稿原先匿名直写 `member_stories`，收敛权限后会失效。新增 `POST /api/hall/story`：校验成员是否公开、限制 10–2000 字、单 IP 每小时 5 条限流，统一按「待审核 / 仅内部可见」入库。
7. **权限批量收敛**：新增 `scripts/tighten-permissions.mjs`，25 张表一次性落库（见 §12），并实测匿名读写 401、会员读写正常。
