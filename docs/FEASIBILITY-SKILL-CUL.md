# Skill 与 CUL 命令行封装可行性评估

| 项 | 内容 |
|---|---|
| 评估对象 | TEDxZizhuPark Team Hub 现有 Web 功能、`/api/**` 服务端能力、`scripts/*.mjs` 运维脚本 |
| 评估日期 | 2026-11-22 |
| 评估目标 | 判断把现有功能封装为 WorkBuddy Skill 与 CUL 命令行入口的可行性，服务组长/成员使用，并让智能体稳定调用 |
| 结论 | **建议封装，但必须分层、渐进、有条件封装**：先只读与纯函数能力，再服务端化核心写链路，最后才开放高影响操作给 Skill |
| 术语假设 | 本文将 **CUL** 理解为“面向团队业务的命令行统一入口（Command-line Utility Layer）”，即一个供智能体与管理员确定性调用的 CLI；若 CUL 另有既定含义，只需替换命令名，架构结论不变 |

---

## 0. 核心结论摘要

1. **可行性成立，但不是“把 UI 操作翻译成命令”这么简单。** 当前核心写逻辑大量位于 React 组件回调中，服务端角色校验只覆盖 `/api/**`，浏览器侧仍可通过 Appwrite SDK 直写数据。直接把这些写接口暴露给 CLI/Skill，会把已知的越权与重复计分风险带入自动化链路。
2. **最适合第一批封装的是只读、确定性、已有纯函数实现的能力**：积分/任务/月报/成员/活动查询与 CSV 导出、`.ics` 生成、CSV 模板与校验、积分规则试算、飞书同步状态/日志、现有运维脚本纳管。
3. **Skill 与 CUL 应分工明确**：Skill 承载业务知识、触发条件、确认策略和多步工作流；CUL 承载稳定命令、参数校验、JSON 输出和退出码；服务端 service 层承载鉴权、幂等、审计和事务语义。
4. **普通成员不适合直接使用 CLI。** 对组长/成员，主入口仍应是自然语言 Skill 与现有 Web UI；CLI 主要面向智能体、管理员和自动化脚本。
5. **建议采用项目级 Skill**（`.workbuddy/skills/team-hub/`），因为它依赖本项目专属的表结构、枚举和口径；个人级 Skill 适合通用能力，不适合本项目强耦合数据语义。
6. **总体改造量估计**：P0+P1 约 6–9 人日；覆盖核心写链路的完整方案约 12–17 人日。该估算不含 Appwrite Row Security 全量迁移的额外工作量。

## 1. 评估基线与现状约束

### 1.1 现有架构

| 层 | 现状 | 对封装的影响 |
|---|---|---|
| 前端 | React 19 + Vite 8；`src/App.jsx` 为单页主应用，约 26 万字符，页面与写操作高度耦合 | 不能直接作为 CLI 复用，需要先抽 service 层 |
| 数据层 | `src/api.js` 封装 Appwrite TablesDB；`sgp` 区域端点；25+ 张表；`fetchTable` 每页 100、最多 5000 行；`upsertItem` 显式写行级 `any` 权限 | 查询可做稳定接口；写接口需要先收敛权限语义 |
| 认证 | 飞书 OAuth（HS256 JWT + HttpOnly Cookie `th_session`）与 Appwrite 邮箱密码双通道；`/api/session` 下发 Appwrite 会话密钥 `th_aws` | CLI 环境没有浏览器 Cookie，必须设计独立的设备登录或服务令牌模式 |
| 服务端 | Vercel Functions：`/api/session`、`/api/notify`、`/api/hall/*`、`/api/feishu/*`、`/api/cron/*` | 已有服务端能力可优先包装，鉴权基础较好 |
| 纯函数模块 | `src/csv.js`、`src/ics.js`、`src/rules.js`、`src/audit.js`、`src/api.js` | 可低成本暴露为 CLI 子命令 |
| 运维脚本 | `scripts/provision-feishu.mjs`、`seed-hall.mjs`、`tighten-permissions.mjs`、`rename-teams-to-feishu.mjs`、`fix-task-owner-names.mjs` 等，多数有 `--apply` 预览/执行范式 | 可直接纳管为 `cul ops ...`，但需强制确认与备份 |
| 文档 | `docs/PRD.md`、`docs/OPERATIONS.md`、`docs/AUDIT-2026-11-13.md` | 可作为 Skill 的 `references/` 内容基础 |

### 1.2 已知障碍（来自代码与审计报告）

- **写操作服务端校验缺口**：`docs/AUDIT-2026-11-13.md` §8 P1-1 明确记录：成员、任务、积分、月报等写操作由浏览器用 Appwrite SDK 直接落库，服务端 `requireAdmin` 只保护 `/api/**`。任何已登录成员理论上可绕过 UI 改他人数据或积分。
- **主键不稳定**：多处使用 `Date.now()` 生成任务、成员、月报、积分调整 ID；跨表关联大量依赖中文姓名字符串。智能体难以稳定定位、更新和去重。
- **枚举是中文字符串**：状态、积分类型、成员角色、可见性等存在 `未开始/进行中/待审核/已通过`、`任务贡献/基础参与`、`组长/成员`、`public/internal` 等多套口径。`src/rules.js` 注释已警告 action 必须与中文取值一致，否则规则永不匹配。
- **幂等缺口**：签到积分使用每次新建的随机流水 ID；CSV 导入积分流水使用随机 `txid`。重复执行会造成重复计分。
- **错误契约不统一**：`/api/notify` 可能 HTTP 200 但 payload 为 `failed/skipped`；`syncTable` 失败只 `console.warn`；`removeRow` 吞错。
- **数据边界**：`fetchTable` 静默截断到 5000 行；`AuditPanel` 只显示前 200 条；`HallAdmin` 成员列表只显示前 60 条。

这些障碍决定了：**第一批封装不能包含未经服务端化的核心写操作**。

## 2. 使用场景

| 角色 | 典型场景 | 更适合的入口 | 是否建议 CLI 化 |
|---|---|---|---|
| 组长 | 查看本组本月任务、待审核积分、成员参与情况 | Skill 自然语言查询；CLI 供自动化报表 | 查询类优先 |
| 组长 | 填写/修改月报、登记任务与参与、提交审核 | Web 四步表单为主；Skill 可生成草稿/校验 | 写类需服务端化后 |
| 组长 | 催报、推送进度摘要、同步飞书成员 | Skill 触发 `cul feishu ...` | 建议 |
| 成员 | 查个人积分、贡献明细、年度参与、活动报名/签到 | Skill 自然语言 + Web 页面 | 仅查询与签到，CLI 非主入口 |
| 管理员 | 审核月报、积分入账/调整、批量导入、成员与团队管理 | Web 管理端为主；Skill 用于批量与报告 | 高影响写需确认与审计 |
| 管理员 | 飞书全量同步、通知日志排障、备份与导出 | Skill + CLI | 强烈建议 |
| 管理员 | 纪念馆届次、影像、公开授权维护 | Web 管理端；CLI 用于归档、清单、只读检查 | 只开放低风险子集 |
| 智能体 | “统计 11 月各组工作量并生成汇报”“导出积分流水”“检查飞书同步是否失败” | Skill 理解意图 → CUL 执行 → 结构化结果 | 这是主要获益场景 |
| 自动化任务 | 每日同步、定时催报、周报摘要、数据备份 | Cron + CUL | 建议 |

**判断**：CLI 对普通成员的学习成本偏高；对组长和管理员，CLI 的价值主要在“批量、可重复、可脚本化”的任务。面向终端用户的体验应由 Skill 承担。

## 3. 功能边界

### 3.1 建议第一批纳入（P0）

| 能力域 | 具体内容 | 现有基础 | 风险 |
|---|---|---|---|
| 只读查询 | 积分流水、任务、月报、成员、活动、报名、审计、纪念馆公开数据 | `fetchTable` + 各页面聚合逻辑 | 低，但需脱敏与分页 |
| CSV 导出 | 成员、积分、月报、任务、年度统计、志愿者名录 | `src/csv.js` 的 `toCsv`、`exportCsv` | 中，含邮箱/电话 |
| 本地文件工具 | CSV 模板生成/解析/校验、`.ics` 生成、重复场次展开 | `csv.js`、`ics.js` 已是纯函数 | 低 |
| 积分试算 | 根据任务与规则计算建议积分，不落库 | `src/rules.js` | 低 |
| 飞书只读 | 同步状态、同步日志、事件日志、通知日志 | `/api/feishu/status`、`/api/feishu/logs` | 低 |
| 运维脚本纳管 | `pingCloud`、表计数、版本信息、脚本清单 | 现有脚本 + `api.js` | 低 |

### 3.2 第二批纳入（P1，需薄服务端包装）

- 飞书全量/增量同步、单人同步、催报、进度摘要推送。
- 活动报名列表、签到名单、签到统计；签到动作需先补幂等。
- 纪念馆影像上传/归档/列表；**删除与公开授权暂不开放给通用 Skill**。
- CSV 批量导入：必须先提供 `--dry-run`、逐行错误报告和总量上限。

### 3.3 第三批纳入（P2，需重构后开放）

- 任务创建/状态流转/工时登记。
- 月报草稿、提交、审核通过/退回。
- 积分审核、手动调整、批量入账。
- 成员/团队档案编辑、后备志愿者管理。

这些能力必须先抽成服务端 service，增加角色校验、稳定业务 ID、幂等键和审计日志，再开放给 Skill。

### 3.4 不建议封装或仅保留管理员专用

- 任意表 CRUD / 任意 Appwrite 查询能力：会绕过业务校验和权限模型。
- `seed-hall.mjs` 的清表重建、`tighten-permissions.mjs --apply` 的 ACL 全量变更：破坏性大，应保留在管理员终端并二次确认。
- 看板拖拽、登录页瀑布流、多语言字典、复杂表单交互：强 UI 耦合，CLI 化收益低。
- 任何需要 `APPWRITE_KEY` 的操作：不得下发给普通成员或通用 Skill。

### 3.5 稳定性准入条件

任一能力进入 Skill 前，必须满足：

1. 有稳定、可引用的业务 ID，不能用 `Date.now()` 作为跨系统主键。
2. 写操作有幂等键，重复执行不产生第二笔积分或第二份月报。
3. 角色与归属校验在服务端执行，不依赖前端菜单隐藏。
4. 所有写操作写入 `audit_logs`，操作者来自服务端身份而非命令行参数。
5. 输出为结构化 JSON，错误码稳定。
6. 中文展示文案与内部稳定枚举分离，避免用中文状态做程序判断。

## 4. 交互与接口设计

### 4.1 Skill 包结构

建议采用项目级 Skill：

```text
.workbuddy/skills/team-hub/
├── SKILL.md                    # 触发条件、工作流、确认策略
├── references/
│   ├── schema.md               # 表、字段、关联关系、稳定 ID 规则
│   ├── enums.md                # 中文展示值 ↔ 内部稳定枚举
│   ├── workflows.md            # 月报/积分/活动/飞书等标准流程
│   └── permissions.md          # 角色矩阵与高影响操作清单
├── scripts/
│   └── cul.mjs                 # CUL CLI 入口
└── assets/
    └── templates/              # CSV 导入模板
```

`SKILL.md` 的 frontmatter 必须包含 `name`、`description`、`agent_created: true`。`description` 用第三人称写明“何时使用”，例如：“当需要查询 TEDxZizhuPark Team Hub 的积分、任务、月报、活动数据，或执行飞书同步、CSV 导入导出、积分试算时使用本技能。”

详细表结构和流程放在 `references/`，由 Skill 按需加载，避免 `SKILL.md` 超过 5k 词。

### 4.2 CUL 命令面

统一形式：`cul <资源> <动作> [选项]`。

| 命令组 | 示例 | 说明 |
|---|---|---|
| 身份 | `cul auth login --provider appwrite`、`cul auth status` | 不保存明文密码；支持设备码或短期令牌 |
| 查询 | `cul points list --member <id> --year 2026 --json` | 只读，支持过滤、分页、排序 |
| 报表 | `cul reports list --month 2026-11 --team <id>` | 只返回本角色可见范围 |
| 任务 | `cul tasks list --team <id> --status in_progress` | 使用稳定状态枚举，不用中文字符串 |
| 活动 | `cul events ics <event-id> --out ./event.ics` | 复用 `src/ics.js` |
| 积分试算 | `cul points preview --task-file task.json` | 只计算，不落库 |
| 导入导出 | `cul csv template members`、`cul csv import tasks --file x.csv --dry-run` | 默认预览，写入需 `--apply` |
| 飞书 | `cul feishu sync --full`、`cul feishu notify digest --dry-run` | 包装现有 `/api/feishu/*` |
| 纪念馆 | `cul hall terms list`、`cul hall media archive --id <id> --term <term-id>` | 不含删除/公开授权 |
| 审计 | `cul audit list --actor <id> --limit 100` | 服务端身份决定可见范围 |
| 运维 | `cul ops ping`、`cul ops counts`、`cul ops scripts` | 连接自检与脚本清单 |

### 4.3 输出契约

所有命令统一输出：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "warnings": [],
  "meta": {
    "requestId": "req_...",
    "actor": "u_...",
    "role": "leader",
    "at": "2026-11-22T12:00:00+08:00",
    "dryRun": true
  }
}
```

约定：

- `--json` 输出机器可读结果；默认人类可读表格。
- 退出码：`0` 成功；`1` 业务失败；`2` 参数错误；`3` 认证/授权失败；`4` 冲突或幂等拒绝；`5` 网络/服务端错误。
- 所有写命令默认 `--dry-run`；真正写入必须显式 `--apply` 或经 Skill 确认后追加。
- 高影响操作必须提供 `--idempotency-key`，服务端按 key 去重。
- `--lang zh|en` 只改变展示文案，内部枚举保持不变。
- 导出含个人信息时默认脱敏；需要完整字段必须 `--include-pii` 并写审计。

### 4.4 认证设计

| 模式 | 适用对象 | 说明 |
|---|---|---|
| 用户令牌 | 组长/成员/管理员 | `cul auth login` 获取短期令牌；CLI 不落明文密码；token 存系统密钥链或环境变量 |
| 服务令牌 | 自动化脚本、服务端任务 | 仅管理员签发，最小权限，带过期时间 |
| CRON 密钥 | 定时任务 | 仅用于 `/api/cron/*`，不进入普通 Skill |
| 服务账号密钥 | 运维 | `APPWRITE_KEY` 只在管理员本机环境变量中使用，禁止写入 Skill 包或仓库 |

**禁止**让 CLI 直接复用 `src/api.js` 的浏览器 SDK 直写通道作为通用写路径。

## 5. 智能体调用链路

推荐链路：

1. **触发**：用户自然语言请求命中 Skill 的 `description`，Skill 被加载。
2. **规划**：Skill 读取 `references/enums.md` 与 `workflows.md`，把中文口语转成稳定资源/动作/枚举。
3. **预检**：智能体先执行只读命令确认对象存在与当前状态，例如 `cul members get --name "林小满"`。
4. **预览**：写操作先 `--dry-run`，返回将变更的记录、积分影响和潜在冲突。
5. **确认**：高影响操作向用户展示摘要并等待明确确认；成员公开、积分扣减、删除、批量导入必须确认。
6. **执行**：CUL 调用服务端 API；服务端完成角色校验、归属校验、幂等、审计。
7. **校验**：智能体检查退出码与 `meta.requestId`，必要时用只读命令复核结果。
8. **汇报**：返回人可读摘要，附 `requestId` 供排障；失败时不得自动重试写操作，除非带同一幂等键。

失败处理规则：

- `403` 不重试，提示用户切换账号或申请权限。
- `409` 表示冲突/幂等拒绝，先查状态再决定是否继续。
- `429` 使用指数退避，仅对只读请求自动重试。
- `5xx` 记录 `requestId` 并停止，避免半写入后重复提交。

## 6. 依赖与改造成本

| 工作项 | 前置依赖 | 估算（人日） | 备注 |
|---|---:|---:|---|
| CUL CLI 骨架、参数校验、JSON 输出、退出码 | Node 20+、脚本目录 | 1–2 | 先固定输出契约 |

| 写操作服务端化（任务/月报/积分/成员） | service 层抽取、稳定 ID、幂等键 | 3–5 | 与审计报告 P1-1 估算一致 |

| 飞书/纪念馆能力包装 | 现有端点 | 1–2 | 已有守卫可复用 |
| Skill 文档、references、测试与分发 | skill-creator 规范 | 1–2 | 项目级 Skill |
| 回归测试与上线验证 | 测试账号、预览环境 | 1 | 不公开密码 |

**合计**：P0+P1 约 6–9 人日；完整方案约 12–17 人日。若同时启用 Appwrite Row Security 并迁移全部写操作，需另估。

外部依赖：

- Appwrite Cloud `sgp` 端点、项目 ID、数据库结构。
- Vercel Functions 与环境变量（`TEAM_HUB_SESSION_SECRET`、`APPWRITE_KEY`、飞书凭证、CRON_SECRET`）。
- WorkBuddy Skill 规范与项目级 Skill 分发。
- 飞书开放平台权限范围（通讯录、机器人、事件订阅）。

## 7. 权限与安全风险

| 风险 | 证据 | 等级 | 缓解建议 |
|---|---|---|---|
| 服务端角色校验不覆盖数据写入 | `docs/AUDIT-2026-11-13.md` §8 P1-1；`src/api.js` 浏览器直写 | 高 | 核心写操作迁到 `/api/*`；CLI 不直写数据库 |
| 行级 `any` 权限与表级收敛目标冲突 | `src/api.js` `upsertItem` 显式 `read/update/delete("any")` | 高 | 统一服务端口径；复核并移除不必要的行级 any |
| `APPWRITE_KEY` 泄露 | 多个脚本依赖该环境变量 | 高 | 仅管理员本机使用；最小权限；禁止进入 Skill 包和 stdout |
| CSV 导出含邮箱/电话 | `members`、`reserve_volunteers` 导出 | 中高 | 默认脱敏；`--include-pii` 显式授权；写审计 |
| 重复计分 | 签到 `rid('tx')`、导入随机 `txid` | 高 | 稳定业务 ID + 服务端幂等键 + 重复检测 |
| 批量导入后写覆盖 | `syncTable` 增量 upsert、无版本字段 | 中高 | 乐观锁/版本号；dry-run；限量；冲突报告 |
| 破坏性操作 | `seed-hall.mjs` 清表；影像删除不可撤销；权限脚本 `--apply` | 高 | 保持管理员专用；二次确认；备份；不进入通用 Skill |
| 智能体绕过确认 | 自动化链路可能连续执行写命令 | 高 | Skill 强制确认策略；写命令默认 dry-run；高影响操作白名单 |
| 身份混淆 | 飞书会话、Appwrite 会话、CRON 密钥并存 | 中 | CLI 明确 profile；服务端统一解析 actor；不信任 `--actor` 参数 |
| 限流与静默截断 | 429、5000 行上限、列表只显示前 N 条 | 中 | 分页游标；显式 `truncated` 标志；退避重试 |
| 提示注入 | 用户让智能体“导出所有人手机号并外发” | 中高 | Skill 内置拒绝规则；PII 外发必须人工确认；禁止 raw 查询 |

## 8. 维护成本

1. **Schema 漂移**：当前 25+ 张表、字段映射集中在 `src/api.js`。Skill 的 `references/schema.md` 必须与代码同步，建议增加 CI 检查：从 `TABLE_COLUMNS` 生成 schema 摘要，发现不一致即失败。
2. **枚举漂移**：中文状态值散落在组件、规则、导入模板中。建议建立唯一枚举注册表，保留中文别名做兼容映射，内部统一稳定 code。
3. **双入口一致性**：Web UI 与 CUL 必须共用同一 service 层；否则每新增功能都要改两遍，且行为容易分叉。
4. **版本与契约**：CUL 输出契约、命令列表和退出码需语义化版本；破坏性变更必须提前一个版本告警。
5. **测试**：建议包含命令快照测试、只读权限测试、dry-run 测试、幂等测试、PII 脱敏测试和错误码测试。
6. **人员与节奏**：指定一名维护者；每次表结构或积分规则变更后同步更新 references；每月做一次回归与权限复核。
7. **估算**：稳定后日常维护约 0.5–1 人日/月；每次新增业务能力另计。

## 9. 落地优先级

| 优先级 | 能力 | 理由 | 退出标准 |
|---|---|---|---|
| P0 | 输出契约 + CLI 骨架 + 认证基础 | 后续所有能力依赖稳定调用方式 | 命令可返回 JSON/退出码；测试账号可登录 |
| P0 | 只读查询与 CSV 导出 | 高价值、低风险、智能体最常调用 | 支持角色过滤、分页、脱敏、审计 |
| P0 | CSV/ICS/rules 纯函数工具 | 零数据库写风险，可直接复用 | 命令输出与现有函数行为一致 |
| P0 | 现有脚本纳管 | 已有运维资产，接入成本低 | `cul ops scripts` 可列清单并提示风险 |
| P1 | 飞书同步/通知/日志/催报 | 现有端点有服务端守卫 | dry-run 与真实执行分离；日志可查 |
| P1 | 活动签到统计、CSV 导入 dry-run | 高频但需补幂等与校验 | 重复执行不重复计分；错误逐行可见 |
| P1 | 纪念馆只读与影像归档 | 便于内容维护且不触碰删除/公开 | 归档可追溯；公开/删除仍走 Web |
| P2 | 任务/月报/积分/成员写操作服务端化 | 价值最高但必须先修安全边界 | 服务端角色校验、幂等、审计齐全 |
| P2 | 将上述写操作接入 Skill | 用户可用自然语言完成标准流程 | 两名组长试运行通过；无越权/重复写入 |
| P3 | 删除、清表、权限脚本 `--apply`、公开授权 | 破坏性大、使用频率低 | 保持管理员专用，不进入通用 Skill |

## 10. 结论与建议

### 10.1 是否建议封装

**建议封装，但采用“先读后写、先服务层后 Skill、CLI 作为执行层而非数据库直连层”的路线。** 不建议一次性把当前全部 UI 功能批量包装成 Skill，也不建议让 CUL 直接复用浏览器 SDK 的写通道。

### 10.2 建议优先封装的能力

1. 只读查询与 CSV 导出：积分、任务、月报、成员、活动、审计、纪念馆公开数据。
2. 纯函数工具：CSV 模板/解析/校验、`.ics` 生成与重复场次展开、积分规则试算。
3. 飞书只读与通知：同步状态、日志、催报、进度摘要。
4. 运维脚本纳管：连接自检、表计数、脚本清单与风险提示。
5. 待安全边界修复后，再封装任务/月报/积分的标准写流程。

### 10.3 主要风险与缓解

| 主要风险 | 缓解方向 |
|---|---|
| 越权写入 | 写操作服务端化；服务端角色/归属校验；CLI 禁止直写 Appwrite |
| 重复计分与重复导入 | 稳定业务 ID；幂等键；默认 dry-run；服务端去重 |
| PII 泄露 | 默认脱敏；显式 `--include-pii`；审计；禁止外发自动化 |
| 破坏性操作 | 管理员专用；二次确认；备份；不进入通用 Skill |
| 智能体误用 | Skill 明确确认策略；命令白名单；失败不盲目重试；输出 `requestId` |
| 维护分叉 | Web 与 CLI 共用 service 层；schema/enums 单一来源；CI 检查 |

### 10.4 建议的下一步

1. 建立稳定枚举与业务 ID 规范，先解决积分、任务、月报三类核心对象。
2. 实现 CUL 的命令骨架与 JSON 输出契约，先接入只读命令和纯函数工具。
3. 建立项目级 Skill，写入触发条件、确认策略、schema/enums 引用。
4. 选 2 名组长试点“查本组积分/导出月报/飞书催报”三类流程，记录失败与歧义。
5. 试点通过后再启动核心写链路服务端化，按审计报告 P1-1 的建议迁移到 `/api/*`。
